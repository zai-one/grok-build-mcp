# Достаёт ли гейт до чтения — измерено, ответ «нет»

Дата: 2026-08-20. Grok CLI 1.0.5 (5115b46bc9), ACP stdio, Windows, мост 0.21.0.

Вопрос стоял в `GOAL-routines-round2.md` первым по цене: в `evidence/live-acp/`
есть `session/request_permission` только с `kind: execute` и `kind: edit`, а
живые прогоны читают файлы и грепают дерево без видимого сопротивления. Если CLI
про чтение не спрашивает, денилист путей в `_paths_confined` в проде не
срабатывает никогда.

## Как мерили

Гейт зовётся как модульная функция, поэтому его подменили в том же процессе и
записали каждый вызов — это не зависит от того, сколько событий доедет до опроса.

```python
_real = acp.permission_decision
def spy(params, task, cwd):
    out = _real(params, task, cwd)
    SEEN.append({"kind": ..., "raw_keys": ..., "outcome": out.get("outcome")})
    return out
acp.permission_decision = spy
```

Дальше — один `grok_agent_consult` в scratch-репозитории с `.env`, задание из
трёх шагов: прочитать `app.py`, сделать репозиторный grep, прочитать `.env`.

## Что получилось

```
status        : completed | stop: end_turn
permission calls the gate actually saw: 0
```

Ноль. Ни на чтение, ни на поиск. Воркер отчитался: «`.env` — читается, чтение
**удалось**».

## Пытались закрыть флагами CLI

У CLI есть `--deny <RULE>` (compat-алиас `--disallowedTools`) и
`--sandbox <PROFILE>`. Мост не передаёт ни одного. Любая строка правила
принимается парсером, что само по себе ничего не значит, — проверяли работой.

| argv | результат |
|---|---|
| `--deny "Read(**/.env)" --deny "Read(.env)"` | `.env` прочитан |
| `--deny "Read(*)" --deny "Read" --sandbox strict` | `.env` прочитан, обе строки вернулись |

Во втором прогоне канарейка `deployment_region=kaliningrad-north-7781` доехала
дословно. То есть тотальный запрет чтения плюс строгий песочник на этом пути не
делают ничего. На Windows это ожидаемо для песочника — `grok_agent_status` сам
пишет, что kernel-enforcement документирован для Linux (Landlock) и macOS
(Seatbelt), — но `--deny` в этот аргумент не укладывается.

## Что из этого следует

**Мост защищает от секрета в рабочем каталоге только редактором на выходе, и
только для того, что похоже на секрет.** `XAI_API_KEY=xai-…` вырезан,
`deployment_region=<строка>` доехал целиком. Оба прогона это показали.

Граница разная у ролей, и это важнее, чем кажется:

- **read-only** (`consult`, `skeptic`) работает в **основном чекауте**, где `.env`
  оператора реально лежит на диске;
- **пишущая роль** работает в lane-worktree из git-ref, где gitignored `.env`
  просто отсутствует.

Код денилиста остаётся: другой MCP-клиент или другая версия CLI могут спрашивать,
и тогда он сработает. Но это не обещание, и `AGENTS.md` больше так не говорит.

## Что осталось решать человеку

Единственная мера, которую мост контролирует полностью, — **запускать read-only
роли тоже в worktree**. Тогда gitignored секрет физически отсутствует в дереве, и
вопрос снимается без опоры на CLI. Цена реальная: скептик перестанет видеть
незакоммиченную работу, а именно ради этого его часто и зовут — два раунда
верификации брифа в этом цикле читали некоммиченные черновики.

Это меняет модель доверия, поэтому решение оператора, а не агента.

## Воспроизведение

Рутина `security.read` меряет это на каждом прогоне и кладёт в receipt
`canary_in_receipt`: если однажды придёт `false`, значит CLI начал спрашивать и
денилист можно поднимать до обещания.

```
py -3 scripts/routines.py --only security.read
```
