# Латентность моста и голодание спавна — замеры 2026-08-21

Стенд: Windows 11, 28 ядер, Python 3.14, Grok CLI 1.0.5, мост 0.24.0.
Каждая строка ниже воспроизводится командой из блока «как повторить».

## 1. Что сколько стоило до правок

| Вызов | Было | Из чего состоит |
|---|---|---|
| `grok_agent_status` | 13 746 / 13 665 / 13 672 / 13 596 мс | `grok models` 12 696 мс + `update_report` 849 мс + `grok --version` 115 мс + git 65 мс |
| `grok_agent_session_begin` (rout. `calls.navigator`) | 14 с | тот же `grok models` внутри `resolve_gate` |
| `grok_agent_project` | 9 мс | чтение файла |
| Диспатч `grok_agent_execute` | мгновенно, lane 377 мс медиана | 4 спавна git |
| Короткий job целиком | 37.7 / 34.0 / 34.0 с | воркер + verifier + коммит |

`grok models` замерен отдельно, три раза: 12.76 / 12.80 / 12.72 с. Это цена
самого CLI (сетевой round trip), мост её не создаёт — но платил её каждый раз.

## 2. Голодание спавна: воспроизведение симптома из routines

Отчёт из routines: тики проходят примерно в половине случаев, preflight
28 / 31 / 48 / 51 / 61 / 75 с при бюджете 60 с. Симптом воспроизведён здесь:

```
prepare_worktree, простаивающий процесс ........... 0.46 с
prepare_worktree, 16 занятых потоков .............. 39.4 / 46.6 / 45.7 с
```

Это тот же диапазон. Причина — не антивирус и не диск: `Popen` голодает по GIL.

| Условие | `Popen(['git','--version'])`, медиана 7 |
|---|---|
| простаивающий процесс | 5.7 / 5.9 / 5.6 мс |
| 16 потоков, интервал по умолчанию (0.005) | 1280 / 1920 / 1526 мс |
| 16 потоков, `switchinterval` 0.0005 | **22.9 / 22.5 / 24.4 мс** |
| 16 потоков, `switchinterval` 0.02 | 3160 / 5547 / 3069 мс |
| 16 потоков, `switchinterval` 0.1 | 9167 / 12402 / 13982 мс |

Направление монотонное, значит это не артефакт. Цена короткого интервала
измерена отдельно: байткодный цикл теряет 50 % пропускной способности, разбор
JSON — 79 %. Поэтому окно открыто **только на спавн**, а не на процесс.

## 3. После правок

| Что | Было | Стало |
|---|---|---|
| `Popen` git под нагрузкой | 1280–1920 мс | 37–51 мс |
| `prepare_worktree` под нагрузкой | 39.4–53.0 с | 22.4–27.5 с |
| `grok_agent_status`, повторный вызов | 13.7 с | 0.91–1.12 с |
| `grok_agent_status`, первый вызов после паузы хоста | 13.7 с | 1.12 с |
| `session_begin` (`calls.navigator`) | 14 с | 1 с |
| Опрос в этом проекте, байт на проводе | 30 836 | 5 382 |

Остаток в 22 с под нагрузкой — это уже не спавн (37–51 мс) и не чтение труб
(71–258 мс), а обычный питоновский код `prepare_worktree`, делящий GIL с
шестнадцатью занятыми потоками. Синтетика: в реальном мосте конкурирует один
поток-читатель ACP, а не шестнадцать.

## 4. Что проверено и не подтвердилось

**Утечка процессов.** Отчёт: «каждый вызов инструмента оставляет за собой
процесс, было 5 — стало 6». На этой машине не воспроизводится:

- перепись показала 5 `grok-delegate.exe`, у каждого **живой родитель**
  `claude.exe` — по одному на открытую сессию, 0.00 с CPU, 1 поток;
- клиент завершился штатно → мост исчез за < 3 с;
- клиент убит `kill` → мост исчез за < 3 с;
- клиент убит **во время работы job'а** (жив был воркер `grok`) → и мост, и
  воркер исчезли за < 10 с.

Вывод: мост умирает вместе со своим клиентом, включая середину job'а. Если на
том хосте процессы копятся — считать надо родителей: либо это по одному мосту
на живую сессию, либо клиент там держит трубу открытой.

## 5. Как повторить

```
py -3 -m pytest tests/test_spawn_priority.py tests/test_auth_probe_cache.py -q
py -3 scripts/routines.py --harness-only
py -3 scripts/soak.py
```

Скрипты замеров лежат в scratchpad сессии и в репозиторий не едут: они
одноразовые, а то, что должно жить, оформлено тестами и рутинами.
